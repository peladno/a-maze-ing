## I. まえがき

迷路は何千年も人間を魅了してきた。ギリシャ神話でダイダロスがミノタウロスを閉じ込めるために造った伝説の
**クノッソスの迷宮**から、現代のパズル本やビデオゲームまで、迷路は常に神秘・挑戦・巧妙な設計の象徴だった。

計算機科学において、迷路生成は単なる遊びではない。アルゴリズム・乱数・グラフ理論の実践的な応用である。
迷路生成に使われる有名なアルゴリズム(*Prim 法*、*Kruskal 法*、*再帰的バックトラッカー*)は、
ネットワーク設計や手続き的コンテンツ生成といった実世界の問題にも使われている。
興味深いことに、**完全迷路**(任意の 2 点間の経路がちょうど 1 本)はグラフ理論の**全域木**と直接に対応する。

迷路を作ること、特に可視化して共有できる迷路を作ることは、
コンピュータが混沌から構造を生み出す様子を体験する良い方法であり、しかも少し楽しい。

> *「迷宮とは、迷うための場所ではなく、道を見つけるための場所である。」* — 作者不詳

## IV. 必須パート

### IV.1 概要

設定ファイルを受け取り、迷路を生成し(場合により**完全迷路** — 入口と出口の間の経路がちょうど 1 本)、
**16 進数によるウォール表現**でファイルに書き出す Python の迷路生成器を実装する。
さらに迷路の**視覚的表現**を提供し、**生成ロジックを後から再利用できる**ようコードを構成する。

### IV.2 実行方法

プログラムは次のコマンドで実行できなければならない:

```bash
python3 a_maze_ing.py config.txt
```

- `a_maze_ing.py` がメインプログラムファイル。**この名前を使わなければならない。**
- `config.txt` は唯一の引数。迷路生成のオプションを定義するプレーンテキストファイル。ファイル名は変えてよい。

プログラムはすべてのエラーを丁寧に処理しなければならない:不正な設定、ファイルが見つからない、
構文エラー、実現不可能な迷路パラメータなど。
**予期せずクラッシュしてはならず、常にユーザに明確なエラーメッセージを示すこと。**

### IV.3 設定ファイルの形式

設定ファイルは 1 行につき 1 つの `KEY=VALUE` の組を含む。
`#` で始まる行はコメントであり、無視しなければならない。

必須キー:

| キー | 説明 | 例 |
| --- | --- | --- |
| `WIDTH` | 迷路の幅(セル数) | `WIDTH=20` |
| `HEIGHT` | 迷路の高さ | `HEIGHT=15` |
| `ENTRY` | 入口の座標 (x,y) | `ENTRY=0,0` |
| `EXIT` | 出口の座標 (x,y) | `EXIT=19,14` |
| `OUTPUT_FILE` | 出力ファイル名 | `OUTPUT_FILE=maze.txt` |
| `PERFECT` | 完全迷路かどうか | `PERFECT=True` |

有用であれば追加のキー(seed、algorithm、display mode など)を足してよい。

**デフォルトの設定ファイルを git リポジトリに用意しなければならない。**

### IV.4 迷路の要件

- 迷路はランダムに生成されるが、**シードによる再現性が必須**。
- 各セルは東西南北(North, East, South, West)の各方位に **0〜4 枚の壁**を持つ。
- 迷路は**妥当(valid)**でなければならない。すなわち:
  - 入口と出口が存在し、互いに異なり、迷路の範囲内にあること。
  - 構造が**完全な連結性**を持ち、孤立セルがないこと(後述の「42」パターンを除く)。
  - 入口と出口は特定のセルであるため、**外周には壁がなければならない**。
  - 生成データは**整合的**であること。隣接する 2 セルは、共有する壁について同じ状態を持たねばならない。
    例:あるセルが東側に壁を持つのに、その壁の向こう側のセルが西側に壁を持たない、という状態は禁止。
- 迷路に**大きな開放領域があってはならない。通路の幅は 2 セルを超えてはならない。**
  例:2x3 や 3x2 の開放領域は可、**3x3 は不可**。
- 視覚的に表現したとき(V 章参照)、迷路には**完全に閉じたセルによって描かれた「42」の文字が見えなければならない**。
- `PERFECT` フラグが有効なとき、迷路は入口と出口の間に**ちょうど 1 本の経路**を持たねばならない
  (= 完全迷路。ループが一切ない)。
- `PERFECT` フラグが無効なとき(**これがデフォルト**)、迷路は代わりに
  **パックマン風ゲームにそのまま使える盤面**でなければならない。具体的には:
  - **すべての通路が到達可能**(完全連結)。盤面全体をパックガムで埋めても攻略可能であること。
  - **四隅と中央が開いた通路**であること(ゴーストとスーパーパックガムが隅に、プレイヤーは中央から開始する)。
  - **少なくとも 2 本の独立した経路(ループ)**を提供すること。追われているプレイヤーが常に代替路を持てるように。
    したがって、完全迷路や、壁を 1 枚だけ壊した完全迷路(ループが 1 本だけ)は**このモードでは不可**。
  - **行き止まりは稀であるべき**(数個は許容)。**行き止まりが 1 つもない**盤面が理想で、ボーナスとして評価される
    (VIII 章参照)。

> **ℹ️ 迷路のサイズが小さすぎて「42」パターンを入れられない場合は、省略してよい。
> その場合はコンソールにエラーメッセージを出力すること。**

### IV.5 出力ファイルの形式

迷路は**1 セルにつき 1 桁の 16 進数**で出力ファイルに書き込む。各桁はどの壁が閉じているかを符号化する:

| ビット | 方位 |
| --- | --- |
| 0 (LSB) | North(北) |
| 1 | East(東) |
| 2 | South(南) |
| 3 | West(西) |

- **壁が閉じているとビットが 1、開いていると 0。**
  例:`3`(2 進 `0011`)は**南と西の壁が開いている**ことを意味する。
  `A`(2 進 `1010`)は**東と西の壁が閉じている**ことを意味する。
- セルは行ごとに格納し、**1 行につき 1 行分**を書く。
- **空行を 1 つ挟んだ後**、以下の 3 要素を 3 行で出力ファイルに挿入する:
  - 入口の座標、出口の座標、そして入口から出口への**最短の妥当な経路**。
    経路は `N`, `E`, `S`, `W` の 4 文字で表す。
- **すべての行は `\n` で終わること。**

出力例:

```text
913955111155551551539515 3
ac2a9102829113855692c3a92
...
c44556c6c555455546c446c46

1,1        # entry  (x,y)
19,14      # exit   (x,y)
ESEENEEESSSEESESSESESSSSEEEEESES
```

> **訳注:** 上のグリッドは原文のスクリーンショットからの抜粋で、桁数は正確でない可能性がある。
> 形式の理解にのみ使い、値の検証には使わないこと。

この出力ファイルは、対応する設定ファイルと合わせて Moulinette により自動テストされうる。
本 subject には**解析スクリプト `maze_analyzer.py`** も付属している。
出力ファイルを渡すと、**ウォールの符号化が整合しているか**(共有する壁が隣接する両セルで同じに符号化されているか)を
検査し、その迷路が(`PERFECT=True` で要求される)**完全迷路**か、
(デフォルトで要求される)**遊べる盤面**(「42」パターン以外に行き止まりがなく、独立した経路が複数ある)かを報告する。
設定ファイルが要求したモードを自分の生成器が本当に満たしているかの確認に使える。

## V. 視覚的表現

プログラムは迷路を視覚的に表示する手段を提供しなければならない。次のどちらかを使う:

- **ターミナルの ASCII 描画**、または
- **MiniLibX (MLX) ライブラリによるグラフィカル表示**

表示は**壁・入口・出口・解の経路**を明確に示すこと。

少なくとも以下の**ユーザー操作**が可能でなければならない:

- 新しい迷路を**再生成**して表示する。
- 入口から出口への妥当な最短経路を**表示/非表示**する。
- 迷路の**壁の色を変更**する。
- 任意:「42」パターンの表示色を個別に設定する。

追加の操作を足してもよい。

> **訳注:** 原文の図では、ターミナル版は迷路の下にメニュー
> (`1. Re-generate a new maze` / `2. Show / Hide the shortest path` / `3. Rotate the wall colours` / `4. Quit`)を出し、
> `Choice? (1-4):` で入力を受ける形になっている。MLX 版は同等の操作をキー入力で行っている。
> どちらを選ぶかは自由なので、ペアで決めて `Docs/pair_communication/` に記録すること。

## VI. コード再利用性の要件

迷路生成は、**将来のプロジェクトで import できるスタンドアロンのモジュール内の、
単一のクラス(例:`MazeGenerator`)として実装**しなければならない。

以下を説明する短いドキュメントを提供すること:

- 生成器のインスタンス化と使い方(**最低限の基本例つき**)。
- カスタムパラメータ(サイズ、シードなど)の渡し方。
- 生成された構造へのアクセス方法、および**最低ひとつの解**へのアクセス方法。

> **ℹ️ この生成器モジュールは迷路の構造へのアクセスを提供するが、
> それは必ずしも出力ファイルと同じ形式である必要はない。**

この再利用可能モジュール全体(コードとドキュメント)は、
後で `pip` でインストールできる**単一のファイル**として利用可能でなければならない。

- パッケージ名は **`mazegen-*`** とし、そのファイルは **git リポジトリのルート**に置くこと。
- 拡張子は `.tar.gz` と `.whl` のどちらも可(Python パッケージの標準ビルドで生成されるもの)。
- フルファイル名の例:`mazegen-1.0.0-py3-none-any.whl`
- **パッケージをビルドするために必要な要素をすべてリポジトリに含めること。**
  評価時に、virtualenv などの環境で必要なツールを入れ、**ソースからパッケージを再ビルドするよう求められる**。

この迷路生成器は後のプロジェクトで再利用される想定なので、
リポジトリのルートに **`LICENSE.md`** を置き、どのライセンスの下でコードを再利用できるかを明記すること。
**ライセンスを選び記述すること自体が課題の一部**であり、ソフトウェアライセンスと知的財産への最初の接触になる。
選ぶライセンスは、後続プロジェクトによる迷路生成器の**再利用と配布を明示的に許可**するものでなければならない。

**メインの `README.md`**(再利用モジュールの一部ではない)にも、この短いドキュメントを含めること。

> **訳注:** 現在リポジトリにあるのは `LICENSE`(拡張子なし)。subject は `LICENSE.md` を要求しているので、
> リネームするかどうかをペアで確認すること。

## VII. README の要件

git リポジトリのルートに `README.md` を用意しなければならない。
目的は、プロジェクトを知らない人(ピア、スタッフ、リクルーターなど)が、
何のプロジェクトか・どう実行するか・どこに詳しい情報があるかを素早く理解できるようにすること。

`README.md` には少なくとも以下を含めること:

- **最初の行**はイタリック体で、次のとおりでなければならない:
  *This project has been created as part of the 42 curriculum by <login1>[, <login2>[, <login3>[...]]].*
- プロジェクトの目的と概要を明確に示す **「Description」** セクション。
- コンパイル・インストール・実行に関する情報を含む **「Instructions」** セクション。
- トピックに関連する定番の参考資料(ドキュメント、記事、チュートリアル等)を列挙し、
  さらに **AI をどのタスク・どの部分に使ったか**を記述する **「Resources」** セクション。
- プロジェクトに応じて**追加セクションが必要になる場合がある**(使用例、機能一覧、技術選定など)。

このプロジェクトで**明示的に要求される追加項目**:

- 設定ファイルの完全な構造と形式。
- 選んだ迷路生成アルゴリズム。
- **なぜ**そのアルゴリズムを選んだか。
- コードのどの部分が再利用可能で、どう使うか。
- チームとプロジェクト管理について:
  - 各メンバーの役割。
  - **当初の計画と、それが最後までどう変化したか。**
  - **うまくいったこと、改善できたこと。**

## IX. 提出とピア評価

いつもどおり git リポジトリで課題を提出する。
**ディフェンスで評価されるのはリポジトリ内の作業だけ。**
ファイル名が正しいか必ず二重確認すること。

評価時に、**プロジェクトの小さな修正**を求められることがある。
軽微な振る舞いの変更、数行のコードの記述・書き換え、簡単に追加できる機能などが考えられる。

この工程は**すべてのプロジェクトに適用されるわけではない**が、
評価ガイドラインに記載がある場合は備えておかなければならない。

これは特定部分についての**実際の理解を検証する**ためのもの。
修正は自分の使い慣れた開発環境で行ってよく、
(評価に特定の制限時間が定められていない限り)**数分で実現可能な範囲**とされる。
例:関数やスクリプトの小さな更新、表示の変更、新しい情報を保持するためのデータ構造の調整など。

詳細(範囲・対象など)は**評価ガイドライン**に明記され、
同じプロジェクトでも評価ごとに異なる可能性がある。

> **訳注:** 「両方の学生が説明でき、その場で修正できる」ことが前提。
> 自分が書いていない側のコードも読んでおく必要がある。`Docs/implementation_plans/` と
> `Docs/learning_log/` はその予行演習の材料になる。
